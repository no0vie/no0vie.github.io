## Build, PDF and reliability coupling

- One build orchestrates Vite, full App SSR, all learning catalogs, all static routes, SEO/sitemap, availability and **mandatory résumé PDFs** (`scripts/build.ts:1–35,41–155,156–220`). Study content changes and PDF/Chromium failures therefore share the same release gate.
- Chromium launch has a 30-second timeout and a 90-second browser-close deadline. Both locale pages use UTC, light theme, reduced motion, JS disabled, print media, A4/tagged PDF; local hyperlinks are rewritten to public URLs (`build.ts:159–210`). Launch, navigation and PDF validation failures are not converted to success. A sandbox workaround is not encoded as a skip-PDF path.
- **Narrow swallowed failure:** font readiness timeout is ignored (`build.ts:195–197`). This can permit fallback-font output. PDF validation checks size/header/trailer/xref only (`scripts/publishing.ts:18–28`), not selectable text, clipping, page count, typography or visual fidelity. Timestamp normalization is not proof of full byte determinism (`publishing.ts:31–36`).
- Historical macOS sandbox Chromium limitations and prior unsandboxed passes are documented at `docs/DECISIONS.md:20`; this audit neither reproduces nor reuses those passes as current evidence.
- Playwright serves already-built output via `scripts/server.ts`, does not reuse an existing server, uses two workers, 30-second test timeout, retained failure traces/screenshots (`playwright.config.ts:4–19`). Running E2E without a fresh successful build can inspect stale output; no fresh build was requested here.
- CI installs Chromium and runs format/lint/typecheck/unit/build/E2E before uploading and deploying Pages (`.github/workflows/publish.yml:26–47`). Only the first deployment attempt is allowed to fail before a retry (`56–66`); this does not suppress quality-gate failures. Screenshot/trace existence has not been checked for this snapshot.
- Reproducible parent checks: package scripts are `format:check`, `lint`, `typecheck`, `test`, `build`, `test:e2e`; `validate` chains them in that order (`package.json:8–21`). **All are NOT RUN by this auditor.** Parent should record exit codes, runtime/browser version and fresh artifacts, including both PDFs and deployed/base-path deep links.

No Study Flow → brnchly dependency was found in inspected learning modules. A Study Flow package embedded “like brnchly” most closely matches **B**, not **D**.

Other seams to make explicit:

- Routing/assets: `import.meta.env.BASE_URL` helpers (`routes.ts:8–22`), Vite base (`vite.config.ts:5–8`), and validated `SITE_URL`/`BASE_PATH` for publishing (`scripts/publishing.ts:1–15`).

- Styling/layout: Study Flow selectors and controls rely on host global CSS/tokens (`src/styles/global.css:1790–1927`); host App supplies shared navigation and PDF link.
- Storage: localStorage is origin-scoped, **not path-scoped**. A same-origin Pages project subpath can retain access to `study-flow:v1`; a new origin cannot. Same-origin copies can also unintentionally share/collide on the key. Moving repositories alone does not migrate or isolate storage.
- Publishing: learning sessions currently inherit résumé metadata fallback and Person structured data from the shared builder (`scripts/build.ts:71–108`); standalone publishing should explicitly separate those responsibilities.
