## 4. P1 — единый статус поиска работы

Реализовать `available | selective | unavailable | unknown`, `updatedAt`, `source: manual | hh`, опционально `verifiedAt`. Статус должен быть явным решением владельца; статус публикации HH не означает активный поиск. Локализованные подписи, например `selective`: «Открыт к интересным предложениям» / “Open to selected opportunities”.

**MVP:** один источник значения в контенте; сборка генерирует `/availability.json` и использует то же значение в RU/EN HTML и PDF, если статус там предусмотрен. Не делать runtime fetch обязательным для статического сайта. Не показывать технические ошибки. Если статус устарел, предусмотрен переход в `unknown` по явно выбранной политике свежести; не переводить автоматически в `available`.

**HH интеграция — только исследовательский этап:** проверить актуальные официальные OAuth permissions, эндпоинты и доступность полей именно для аккаунта соискателя. Не реализовывать парсинг HTML/скрейпинг, не сохранять токены в репозитории/фронтенде. Возможная последующая синхронизация через GitHub Actions или приватный BoRIS backend только после отдельного согласования. Не считать задачу блокером текущего релиза.

## 10. Критерии приёмки

- На `/ru` и `/en` главное достижение подчёркивает архитектурную расширяемость, содержит явную связь архитектуры с 1–2 рабочими днями и приблизительное сравнение с двухнедельным спринтом в старом сопоставимом механизме.

- RU/EN и PDF имеют согласованные факты; сайт читаем на мобильных, с клавиатуры и без JavaScript.
- Публичный availability и `/availability.json` согласованы и не требуют отдельного API в MVP.
- Никаких секретов, внутренних контрактов, непроверенных процентов, несуществующих проектов и необоснованных бизнес-результатов.
