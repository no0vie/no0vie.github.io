# Study Flow — спецификация v1.0

## 0. Назначение и ограничения
Переработать существующую `/interview/` и связанные заметки в удобную последовательность тематических учебных сессий, вдохновлённую перелистыванием Reels/Stories, но без бесконечной ленты и навязчивого autoplay. Одна сессия — связная тема, целевая продолжительность **15–20 минут**; предпочтительно 15–18, мягкий предел 20. Карточка — один тезис/действие, не отдельная сессия. Сохранить доступ к исходным полным материалам и решениям.

**Основание:** приложенный JSON-аудит `/interview/`, locale `ru`, RU/EN, 16 theory / 15 practice / 6 learning paths, оценки 630+940=1570 мин. Это метаданные аудита, а не исходные тексты статей или исходники. Codex обязан прочитать реальные файлы репозитория и сверить содержимое до преобразования.

## 1. UX и маршруты
- `/interview/` становится входом в Study Flow: `Продолжить`, `15–20 минут сейчас`, `Выбрать тему`, `Повторить`, `Все материалы`.
- Сохранить прежние прямые URL через редиректы/совместимые маршруты, не ломать GitHub Pages, RU/EN и навигацию из `/notes/`; провести аудит фактических маршрутов, выбрать единый источник контента, исключить дублирование.
- `/interview/session/:sessionId` (или существующий совместимый формат роутинга): полноэкранная по содержанию, но НЕ обязательный fullscreen, карточка с индикатором `2/6`, временем сессии, категорией, кнопками `Назад`, `Далее`, `К подборке`, `Завершить`. Клавиатура ← →, Escape; на touch — горизонтальный swipe с порогом, не конфликтующий с вертикальной прокруткой и выделением текста. Не листать автоматически. В браузере Back/Forward восстанавливать сессию и карточку.
- Карточки: `hook/question`, `concept`, `diagram`, `worked-example`, `interactive-prediction`, `mini-task`, `answer/reveal`, `pitfall`, `production-case`, `recap`, `self-check`. Не делать длинных текстовых полотен; детали раскрываются по запросу. Любые скрытые ответы доступны через кнопку с aria-expanded.
- Сессия 4–8 карточек, одна основная учебная цель; в конце 1–3 контрольных вопроса, критерии ответа и осмысленная рекомендация следующей сессии. Оценки времени для чтения, анализа схем, выполнения кода, самопроверки учитывать отдельно.
- Прогресс виден, но не поощрять бесконечное пролистывание. Никаких streak, наказаний, бесконечного autoplay, таймеров, блокирующих продолжение.
- На мобильном 375px — один фокусный блок, крупные цели касания; 768/1024/1440; светлая/тёмная темы, print, prefers-reduced-motion, фокус, контраст, скринридеры.

## 2. Содержание и редакционная модель
- Единая типизированная сущность `LearningSession` с `id`, `version`, `locale`, `title`, `goal`, `category`, `tags`, `difficulty`, `estimatedMinutes`, `cards`, `sourceTopicIds`, `sourceExerciseIds`, `prerequisiteSessionIds`, `relatedSessionIds`, `conceptIds`, `reviewPolicy`, `sources`, `updatedAt`.
- Карточка: стабильный `id`, `kind`, локализованное содержимое, `estimatedMinutes`, опциональные `diagram`, `codeChallenge`, `assessment`. Сумма карточек + overhead на навигацию/рефлексию соответствует длительности сессии; валидация 15–20 мин для обычных сессий. Для исключений — явная редакторская причина и разбивка при первой возможности.
- Сохранять исходные `topicId`, `exerciseId` как ссылки provenance. Не дублировать статьи вручную; определить один canonical content layer, из которого можно показывать и flow, и полноформатный справочник.
- RU/EN parity: одинаковые id и концепты, естественные локализованные заголовки; fallback с явным уведомлением, если перевод ещё не готов; не публиковать пустые заглушки.
- Теория: краткий ответ 30–60 сек, механизм, схема, пример, антипример/ограничения, production trade-offs, контрольный вопрос. Для сложных кейсов несколько сессий с логическим продолжением.
- Не обрезать исходные упражнения 45–105 минут: разбить на **этапы с независимым результатом** (постановка/контракты, алгоритм, реализация части, тесты, review). Полное решение и оригинальная задача доступны в `Все материалы`.
- Сложные задачи: кодогенерация уникальных **вариантов** на основе детерминированного seed, параметров и эталонных тестов. Не использовать LLM runtime, внешние API или непроверенный eval. Генератор обязан гарантировать решаемость, непротиворечивые условия и ожидаемый результат. При отсутствии безопасного генератора — банк проверенных вариантов.

## 3. Схемы и иллюстрации
- Для каждой темы редактор решает, нужна ли схема; обязательна для flow/state/timing/architecture тем (DNS/TLS/HTTP/render, Event Loop, Fiber, MV*, MobX/Redux, микрофронтенды, idempotency, messaging, concurrency).
- Выбирать Mermaid для простых flowcharts/sequence, SVG/React для интерактивных диаграмм, код/таблицу для точных примеров. SVG accessible title/description, текстовая альтернатива, адаптивность и zoom; экспорт/print. Не генерировать декоративные схемы, не подменять техническую точность визуальной привлекательностью.
- Генерация схем — из структурированных данных или шаблонов, затем проверка автором/тестами: корректность порядка событий, подписей, причинно-следственных связей, dark/light, RU/EN.
- Рисовать схему там, где она помогает ответить на вопрос, а не просто ради наличия иллюстрации.

## 4. Расписание, тасование и localStorage
- Только локальное хранилище с версионированным ключом `study-flow:v1`, валидация схемы, миграция старых статусов (четыре статуса аудита — фактические значения выяснить в коде), обработка corrupt data, disabled storage и приватного режима.
- Данные по `sessionId` и `version`: `lastOpenedAt`, `lastCompletedAt`, `visitCount`, `completedCount`, `confidence` (again/hard/good/easy), `dueAt`, `lastCardId`, `answers`/результат self-check (без хранения чувствительных свободных текстов по умолчанию). Глобально: `queueHistory`, `lastCategory`, `schemaVersion`.
- Сохранение просмотра ≠ изучение. Завершение — явное действие + self-check или `Пропустить проверку` с отдельным статусом. Простое пролистывание не засчитывать.
- Алгоритм выбора следующей сессии: (1) непройденные prerequisites; (2) due reviews и слабые ответы; (3) новые темы; (4) разнообразие категорий; (5) продолжение выбранного маршрута. Избегать 2–3 подряд однотипных тем, но не разрывать обязательные зависимости. Балансировать фактическую длительность и когнитивную сложность, а не только количество карточек.
- Простая прозрачная система интервального повторения (например again: завтра, hard: 3 дня, good: 7, easy: 14; настраиваемая/обоснованная, не объявлять научно оптимальной). Рекомендация объясняется: «Повторить — прошло 7 дней», «Следующий шаг после Fiber».
- Детерминированная функция `rankSessions(catalog, progress, now, preferences)` с тестами, без Math.random в логике выбора; seed только для генерации задач. Режим ручного выбора и сброс/экспорт/импорт прогресса в JSON.
- При изменении контента не терять прогресс: стабильные IDs, версия материала и осознанная политика повторного прохождения после существенного изменения.

## 5. Уникальные программные задачи
- Создать декларативный `ChallengeTemplate` с `id`, `generatorVersion`, `seed`, `difficulty`, `generate(seed)`, `validate(instance)`, `referenceSolution`/oracle, `tests`, `hints`, `explanation`, `timebox`.
- Примеры: Event Loop (разные последовательности task/microtask), Promise.all (входы, reject, порядок), concurrency limiter (лимиты/длительности), debounce (leading/trailing/maxWait), autocomplete race (задержки/abort), TypeScript unions (модель состояний), groupBy/indexBy (типовые входы), SQL isolation (расписания транзакций), idempotency (повторные запросы и ключи). Для TS type-level задач проверять типы через tsc/тесты в dev/build, не выполнять произвольный пользовательский код в браузере.
- Уникальность: фиксированный seed на попытку, разные seed дают семантически различимые экземпляры, replay по seed, антидубликаты в пределах разумного окна, ограниченное пространство вариантов и fallback. Не обещать бесконечно уникальные задания.
- Проверять генераторы property-based/табличными тестами на десятках/сотнях seeds, корректность решений, локализацию и воспроизводимость. Не отправлять пользовательский код на сервер.
- System design/behavioral: уникальные параметры сценария и ограничения, не псевдослучайная «единственно правильная» архитектура; оценка по рубрике, компромиссам и красным флагам.

## 6. Skill для Codex
Создать `.agents/skills/study-flow-content/SKILL.md` (если в репо другой стандарт скиллов, следовать ему) + шаблоны и проверочные скрипты. Скилл должен:
1. Аудировать каталог, существующие связи, сложность и реальные длительности.
2. Принимать новую тему/исходную заметку/задачу/результат мок-интервью; определять, дополнить существующую сессию, создать новую или разделить старую.
3. Строить граф концептов, prerequisites, related, practice и проверять циклы/висячие ссылки.
4. Разбивать материалы на сессии 15–20 мин, без потери смысловой полноты, создавать RU/EN, короткие ответы, примеры, self-check, схемы и source citations.
5. Для кодовых тем создавать генератор задач либо документировать невозможность/выбирать банк вариантов; обеспечивать oracle и тесты.
6. Запускать content lint, Zod/schema validation, link/diagram validation, генераторные тесты, сборку, smoke тесты.
7. Уметь **реорганизовать весь поток** по новым данным без потери stable IDs и localStorage; выводить migration map и diff/coverage report.
8. Выдавать отчёт: добавленные/разделённые/перемещённые сессии, длительности, неразрешённые пробелы, ссылки на источники, результаты тестов.

## 8. Этапы реализации и acceptance criteria
**Phase 0 — Audit**: обследовать существующие роуты, типы, Zod, прогресс, notes, задачи, рендерер и тесты; составить inventory и mapping; ничего не потерять.
**Phase 1 — Vertical slice**: 3–4 завершённые сессии из Browser/Event Loop/React; маршруты, карточки, keyboard/swipe, diagram, self-check, localStorage migration, 1 генератор уникальных задач. Проверить UX на 375/768/1440.
**Phase 2 — Full migration**: мигрировать 16 тем + 15 практик в связные 15–20-минутные сессии (число сессий определяет контент, не фиксировать заранее); сохранить исходные full-length материалы; устранить семь shallow тем; RU/EN; редакторские маршруты.
**Phase 3 — Skill & generators**: добавить скилл, шаблоны, генераторы для подходящих типов задач, миграции и content lint; report.
**Phase 4 — Polish**: ручная калибровка времени, доступность, reduced motion, производительность, edge cases, CI.

Приёмка: все исходные ID имеют покрытие в flow или явную причину исключения; не потеряны условия/подсказки/решения; обычные сессии 15–20 мин; можно перейти вперёд/назад без возврата в каталог; resume после reload; нет случайных повторов в рекомендованной очереди; контрольный вопрос отделён от простого просмотра; диаграммы технически корректны; генераторы воспроизводимы; RU/EN и light/dark; прямые ссылки GitHub Pages; tests/build green; отчёт Codex с реальными проверками, без выдуманных результатов.

## 9. Что не делаем в v1
Backend-аккаунты, синхронизация между устройствами, LLM в браузере, социальные механики, публичный рейтинг, обязательные streak, запуск произвольного кода в браузере, замена полного справочника только карточками.
